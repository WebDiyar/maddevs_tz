- **Состояния:** скелетон при загрузке, пустой день, ошибка с кнопкой «Повторить», индикатор отправки формы.

## Баги

1. **Сервер принимает несуществующую дату.** `POST {"date":"2026-11-31"}` → `201`, бронь сохраняется на 31 ноября. `GET ?date=2026-02-31` отвечает `200 []` вместо `400`. Проверка смотрит только на формат `YYYY-MM-DD`, а не на то, что такая дата есть в календаре.
2. **Сервер принимает время не по сетке 15 минут.** `10:07–10:52` → `201`. Рекрутер сказал «шаг 15 минут», но это проверяет только интерфейс. Если открыть такую бронь, поля «Начало» и «Окончание» в форме пустые (проверил в браузере), потому что в списках нет `10:07`.
3. **Страница 404 не оформлена и не переведена.** По `/nope` показывается стандартное английское «This page could not be found.» даже при выбранном русском.
4. **Мелочь:** ошибки формата от сервера частично на английском даже в русском режиме: «Некорректные данные в поле title: *Too big: expected string…*». Это стандартные тексты zod, их не перевели.
5. **Мелочь:** если поменять язык при открытой форме с ошибкой, уже показанная ошибка остаётся на старом языке до следующей проверки поля.

Баги 1 и 2 воспроизводятся только запросом в обход интерфейса. Но ТЗ говорит «сервер валидирует бизнес-правила», и проверяющий может отправить такой запрос через curl.

## Удобство

### 5. Занятое время отключено в списке «Начало»
**Сейчас:** можно выбрать 10:30, когда 10:00–11:00 занято, и только после этого появится ошибка «Пересекается с бронью…».

**Варианты:**
- **А. Отключать занятые варианты.** Начало недоступно, если с него нельзя забронировать хотя бы 30 минут. Окончание недоступно, если отрезок от начала до него задевает чужую бронь.
- **Б. Отключать и подписывать,** например «10:30 — занято (Планёрка)». Понятнее, но список становится шумнее.
- **В. Не отключать, а подсвечивать** занятые варианты цветом. Выбрать их можно, ошибка будет как сейчас.

**Работа:** ~30 минут. Вся логика уже есть в `isStartFree`, её надо подключить к спискам.
**Совет:** **А**. Это прямо про ТЗ («аккуратная работа с бизнес-логикой»), и ошибок станет меньше.

### 6. Дата в URL (`/?date=2026-10-23`)
**Даёт:** после перезагрузки остаёшься на том же дне, ссылкой на день можно поделиться, работают кнопки браузера «назад» и «вперёд».

**Варианты:**
- **А. Обычный `useSearchParams` и `router.replace`.** Без новых библиотек, история браузера не засоряется.
- **Б. То же через `router.push`.** Каждый день попадает в историю, и «назад» листает дни. Может раздражать.
- **В. Библиотека `nuqs`.** Удобно и типизировано, но это новая зависимость ради одного параметра.

**Нюанс:** при Next 16 со статической страницей `useSearchParams` требует обернуть страницу в `<Suspense>`. Это несложно.
**Работа:** ~30–40 минут.
**Совет:** **А**. Неправильную дату в URL (`2026-13-45`) молча заменять на сегодняшнюю.

### 7. Выделение интервала мышью на таймлайне
**Даёт:** провёл мышью от 10:00 до 11:30, и открылась форма с этим временем. Так работают Google Calendar и Outlook.

**Варианты:**
- **А. Свои обработчики pointer-событий,** с привязкой к шагу 15 минут. Ограничения видны прямо при протягивании: не больше 2 часов, нельзя через чужую бронь.
- **Б. Библиотека календаря** (FullCalendar, react-big-calendar). Много готового, но тяжело, её надо стилизовать под shadcn и подстраивать под наши правила.
- **В. Без протягивания:** первый клик задаёт начало, второй — окончание. Проще, и с телефона удобнее.

**Работа:** А — 2–3 часа (сложнее всего сенсорные экраны и доступность). В — около часа.
**Совет:** если делать, то **А** только для мыши, а на мобильном оставить текущий клик по ячейке. Для тестового это заметный плюс, но рискованный по времени.

### 8. Сводка дня

**Варианты:**

**Работа:** А — 20 минут, Б — около часа.

### 9. «Отменить» после удаления
**Варианты:**
- **А. Повторное создание.** В тосте кнопка «Отменить», которая отправляет `POST` с теми же данными. Минус: у брони новый `id`, а за это время слот могут занять (тогда придёт 409, и это корректно).

**Работа:** А — 30 минут, Б — около часа.
**Совет:** **А**, но вместе с текущим диалогом подтверждения можно получиться лишняя защита. Либо **А без диалога**: так делают Gmail и Linear.

### 13. Оптимистичные обновления
**Сейчас:** нажал «Забронировать», ~400 мс крутится спиннер, потом бронь появляется.

**Варианты:**
- **А. Полный оптимизм:** бронь сразу появляется на таймлайне, при ошибке откатывается. Проблема с нашим ТЗ: при 409 бронь сначала появится, потом исчезнет, и это выглядит хуже честного спиннера. Пункт 8 ТЗ прямо про такой сценарий.
- **Б. Оптимизм только для удаления и изменения названия,** где конфликт почти невозможен. Создание и перенос остаются с ожиданием ответа сервера.
- **В. «Черновик» на таймлайне:** пока идёт запрос, бронь показывается полупрозрачной с надписью «сохраняем…». При успехе становится обычной, при 409 исчезает вместе с сообщением. Честно и быстро.
- **Г. Не делать:** ответы и так быстрые, а логика с откатами усложняет код.

**Работа:** Б — около часа, В — 1–1,5 часа (через `useMutationState` в TanStack Query).
**Совет:** **В** для создания и изменения плюс **Б** для удаления. Если хочется проще, то **Г**: ТЗ оценивает корректность, а не мгновенность.

### Ещё про скорость, дёшево

## Пункт 9 простыми словами

Сейчас удаление идёт в два шага: «Удалить» → окно «Удалить бронь?» → «Удалить». Альтернатива — как в Gmail: удаляешь сразу, без окна, а внизу на 5 секунд появляется «Бронь удалена · **Отменить**». Нажал «Отменить», и бронь вернулась.

Проблема в возврате: сервер её уже удалил. Значит, «Отменить» отправляет новый запрос на создание с теми же данными. Если за эти секунды время кто-то занял, вернуть не получится (придёт 409, это корректно). У брони будет новый `id`, пользователь этого не заметит.

Делать стоит, только если убрать окно подтверждения, иначе получится двойная защита. Для тестового текущий вариант с подтверждением надёжнее, я бы оставил его.

## 6. Скорость отклика при сохранении брони

Пользователь заполнил форму и нажал «Забронировать». Вопрос в том, что происходит до ответа сервера (у нас примерно 0,4 с).

**а) Ждать ответа со спиннером (сейчас так)**
- Кнопка показывает спиннер, форма заблокирована. Пришёл ответ — форма закрывается, бронь появляется на таймлайне.
- ➕ Честно: показываем только то, что сервер подтвердил. При 409 форма остаётся открытой, данные сохраняются, всё по п.8 ТЗ.
- ➖ Небольшая пауза. На медленном интернете она будет заметнее.

**б) Сразу показывать бронь (оптимистично)**
- Форма закрывается мгновенно, бронь сразу на таймлайне. Если сервер ответил 409, бронь пропадает, и появляется сообщение.
- ➕ Ощущается мгновенно.
- ➖ Бронь «мигает»: появилась и пропала. Хуже того, форма уже закрыта, поэтому её надо открывать заново с введёнными данными, иначе нарушится п.8 «не потерять данные». Код сложнее: откат, восстановление формы.

**в) Полупрозрачный черновик («сохраняем…»)**
- Форма закрывается сразу, на таймлайне появляется полупрозрачная бронь с подписью «сохраняем…». Сервер подтвердил — она становится обычной. Пришёл 409 — черновик исчезает, форма открывается снова с данными и сообщением.
- ➕ Быстро и честно: видно, что сохранение ещё не подтверждено.
- ➖ Та же сложность с повторным открытием формы при 409, около 1–1,5 часа работы.

**Мой совет:** **а**. ТЗ оценивает корректность обработки конфликтов, а не мгновенность, и при 409 форма ни разу не закрывается. Для **б** и **в** нужно уметь заново открывать закрытую форму, а это лишний риск.

## 7. Удаление брони

**а) Окно подтверждения (сейчас так)**
- «Удалить» → окно «Удалить бронь? Пятница, 23 октября, 12:00–13:00 · Название» → «Удалить».
- ➕ Случайно удалить невозможно. Просто и надёжно, сервер сразу удаляет бронь.
- ➖ На один клик больше.

**б) Без окна, с кнопкой «Отменить» (как в Gmail)**
- «Удалить» → бронь сразу исчезает, внизу на 5 секунд тост «Бронь удалена · Отменить».
- Есть два способа сделать «Отменить»:
  - **Удалить сразу, по «Отменить» создать заново.** У брони будет новый `id`. Если за эти секунды время кто-то занял, вернуть не получится (придёт 409).
  - **Отложить удаление на 5 секунд.** Бронь только скрыта, а запрос на удаление уходит, когда тост исчез. Но если закрыть вкладку раньше, удаление не дойдёт, а другие пользователи 5 секунд видят «удалённую» бронь.
- ➕ Быстрее и современнее.
- ➖ У обоих способов есть пограничные случаи, кода и тестов больше.

**Мой совет:** **а**. Для тестового это надёжнее и не создаёт новых крайних случаев.

## 8. Конфликт 409 на демо

Пункт 8 ТЗ: «сервер может вернуть конфликт, даже если UI считал слот свободным». Сам по себе конфликт на демо не случится: интерфейс не даёт выбрать занятое время, а проверяющий обычно один. Поэтому mock иногда изображает ситуацию «пока вы заполняли форму, это время занял коллега».

**а) Каждое пятое создание получает 409 (сейчас так)**
- Проверяющий почти наверняка увидит обработку: сообщение в форме, данные сохранены, на таймлайне появилась бронь «Занято коллегой».
- ➕ Обработка 409 видна сразу, без инструкций.
- ➖ Проверяющий может принять это за баг. Поэтому предупреждение есть в README и на `/about`.

**б) Выключить на демо, 409 только при реальном пересечении**
- Конфликт можно увидеть, только если открыть две вкладки и одновременно забронировать одно время.
- ➕ Никаких «странных» отказов.
- ➖ Скорее всего, обработку 409 никто не увидит, хотя её специально просят показать.

**в) Реже, каждое десятое создание**
- Компромисс: проверяющий увидит 409 реже, но за несколько броней, скорее всего, наткнётся.
- ➕ Меньше раздражает.
- ➖ Может так и не попасться, если создать 3–4 брони.

**Ещё вариант без вопроса рекрутеру:** **б** + кнопка «Симулировать конфликт» в интерфейсе. Проверяющий сам решает, когда посмотреть на 409. Можно добавить, если ответ будет «б».

**Мой совет:** **а**, раз уже есть предупреждения, или **б с кнопкой**. Тогда 409 видно по желанию, и случайных отказов нет.

Лучше через сайт Vercel, связав проект с GitHub. Так проще: каждый `git push` в `main` деплоит сам, а для каждого PR появляется своя превью-ссылка. Из этой сессии тоже можно, но для `vercel login` нужен вход в браузере, и потом всё равно придётся связывать с GitHub.

## Как сделать через сайт

1. Создай репозиторий на GitHub и запушь проект:
   ```bash
   git add -A && git commit -m "..."   # текст коммита я давал выше
   git remote add origin git@github.com:<логин>/<repo>.git
   git push -u origin main
   ```
2. На vercel.com: **Add New → Project → Import** твоего репозитория.
3. Настройки определятся сами: Framework — Next.js, Build — `npm run build`, Output — по умолчанию. Ничего не меняй.
4. **Deploy.** Ссылку вида `https://<имя>.vercel.app` вставь в начало README вместо «ссылка появится после деплоя».

## Секреты и переменные

**Обязательных нет.** Mock API встроен, внешних сервисов и ключей нет.

**В GitHub Secrets ничего добавлять не нужно.** Токены (`VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`) понадобились бы, только если деплоить через GitHub Actions. При импорте через сайт Vercel сам подключается к GitHub.

**В Vercel, при желании:** Project → Settings → Environment Variables.

| Переменная | Значение | Зачем |
|---|---|---|
| `MOCK_CONFLICT_RATE` | `0.2` (по умолчанию) | Доля случайных 409. Поставь `0.1` или `0`, если рекрутер ответит 8б или 8г |
| `MOCK_LATENCY_MS` | `400` (по умолчанию) | Искусственная задержка ответа, чтобы были видны спиннеры |
| `NEXT_PUBLIC_API_BASE_URL` | не задавать | Нужна только для реального бэкенда |

Если поменяешь переменную, сделай **Redeploy**: новые значения подхватываются только при новом деплое.

## Что учесть

- Данные хранятся в памяти сервера, поэтому на Vercel брони иногда «пропадают» между запросами. Это уже описано в README и на `/about`. Если рекрутеру важна стабильность, могу подключить Upstash Redis через Marketplace в Vercel (бесплатно, переменные добавятся сами).
- `.env`, `docs/local/`, отчёты Playwright в git не попадают, это уже настроено в `.gitignore`.
- e2e-тесты на Vercel не запускаются, только сборка. Если нужно, могу добавить GitHub Actions с `lint:all`, unit и e2e на каждый push. Секреты для этого тоже не понадобятся.

Если всё-таки хочешь задеплоить отсюда: выполни в этом чате `! npx vercel login` и залогинься в браузере, а дальше `vercel --prod` я запущу сам.
