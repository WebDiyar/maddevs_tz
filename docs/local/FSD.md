## 0. Что изменилось в FSD 2.1 (если ты знал v2.0 — читай это)

Релиз 2.1 называется **«Pages first»**. Breaking changes нет — проект на 2.0 остаётся валидным, — но **ментальная модель декомпозиции перевернулась**:

| Было (v2.0)                                                                  | Стало (v2.1)                                                                                                                              |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Сначала выделяем entities и features, из них собираем widgets и pages         | **Начинаем со страниц** — и, возможно, на них и останавливаемся                                                                            |
| Pages — «тонкие» композеры без логики и запросов                              | В слайсе страницы **можно держать сколько угодно кода**: UI-блоки, формы, запросы (`api`-сегмент), пока команде удобно навигироваться      |
| Любое действие пользователя → feature                                         | **Feature — только то, что переиспользуется на нескольких страницах.** Одноразовая «фича» живёт внутри страницы                            |
| Widgets — чисто композиционный слой                                           | Widget может держать **свои сторы, бизнес-логику и запросы**. ⚠️ Позже (июль 2026) доку пересмотрели ещё раз: слой признан нерекомендуемым — см. ниже |
| Основная масса кода — в entities/features                                     | Основная масса кода — в **pages и shared**; вниз выносим только реально переиспользуемое                                                   |

### ⚠️ Что изменилось в доках ПОСЛЕ релиза 2.1 (июль–август 2026)

Версия спецификации осталась **2.1** (в `CHANGELOG.md` последняя запись — 2.1.0 от 31.10.2024), но сама дока продолжает меняться. Главное:

> 🔑 **Слой `widgets` теперь официально не рекомендуется.** В `reference/layers` появился блок-предупреждение: *«This guide discourages using the Widgets layer»* (коммит `docs: discourage the Widgets layer`, 29.07.2026).

**Почему.** В реальном фронтенде «блок UI» почти всегда тащит за собой логику пользовательского сценария — загрузку данных, состояние, обработку событий. Тогда ответственности `features` (пользовательские сценарии) и `widgets` (блоки UI) пересекаются, и граница между слоями перестаёт быть внятной.

**Куда девать код вместо widget'а** — официальный ответ прямо перечисляет варианты, и «просто перенести блок на другой слой» в них не входит:

| Что за блок | Куда |
| --- | --- |
| Композиция, специфичная для конкретного экрана | остаётся в `pages` |
| Действие, переиспользуемое на нескольких страницах | в `features` — **вместе** с UI-композицией, которая нужна для этого действия |
| Общий UI без бизнес-контекста | в `shared` |
| Layout уровня приложения | в `app` |

Слой из спецификации не удалён и проекты на нём остаются валидными — но для нового кода отталкивайся от таблицы выше. В этом гайде разделы про `widgets` помечены соответствующим образом (§3, §10, §12).

Остальные изменения 2.1 и обновления доков:

1. **`@x`-нотация стандартизирована** — официальное имя «Public API for cross-imports» (§6). Раньше была экспериментальным предложением.
2. **Slice groups** — новая официальная страница в Reference: группировка родственных слайсов в папку (§4.1).
3. **`app` и `shared` = «слой и слайс одновременно»** — их сегменты свободно импортируют друг друга (§3).
4. **`shared` смягчили**: запрещена бизнес-*логика*, но «business-themed» UI (логотип компании, layout, autocomplete) — можно (§14).
5. **`index.server.ts`** — environment-specific публичный API для server-only кода (Next.js RSC) (§6).
6. **Next.js: официальная рекомендация** — переименовать оба конфликтующих слоя в `_app` и `_pages` (совместимо со Steiger) (§3).
7. **`processes` официально deprecated** — содержимое переносится в `features` и `app`.
8. **Decomposition cheatsheet убрали из доков** (признан «более вредным, чем полезным») — ссылки на него больше нет.
9. У Steiger появились правила под новую модель: `insignificant-slice` и `excessive-slicing` (§15).
10. Появились **Docs for LLMs** — https://fsd.how/docs/llms — версия доков, которую удобно скармливать AI-ассистентам.

Официальный гайд миграции: https://fsd.how/docs/guides/migration/from-v2-0

## 1. Зачем FSD

FSD даёт **предсказуемую** структуру, которая масштабируется и не превращается в «кашу»:

- код ищется по **бизнес-смыслу**, а не по типу файла;
- модули **слабо связаны** (low coupling) и **внутренне целостны** (high cohesion);
- понятно, **куда** класть новый код и **что от чего** зависит;
- рефакторинг локален: меняешь слайс — не ломаешь остальные;
- новичок находит функциональность, просто пролистав `pages` и `features`.

---

## 2. Три измерения структуры

FSD режет код по трём осям:

| Ось          | Что это                                | Примеры                                                     |
| ------------ | -------------------------------------- | ----------------------------------------------------------- |
| **Слои**     | уровень ответственности (горизонтально)| `app`, `pages`, `widgets`, `features`, `entities`, `shared` |
| **Слайсы**   | бизнес-домен внутри слоя (вертикально) | `user`, `product`, `order`, `home-page`                     |
| **Сегменты** | техническое назначение внутри слайса   | `ui`, `api`, `model`, `lib`, `config`                       |

> Путь к файлу всегда читается как **`<слой>/<слайс>/<сегмент>/...`**, например `entities/user/model/user.ts` или `pages/home/api/get-feed.ts`.

Доки: [Layers](https://fsd.how/docs/reference/layers) · [Slices and segments](https://fsd.how/docs/reference/slices-segments).

## 3. Слои и главное правило импортов

Слои сверху вниз (по убыванию ответственности):

```
app        ← инициализация: роутинг, провайдеры, глобальные стили, аналитика
  ↓
pages      ← страницы целиком: UI + запросы + локальная логика страницы
  ↓
widgets    ← ⚠️ слой НЕ рекомендуется (§0); в существующих проектах — блоки, переиспользуемые между страницами
  ↓
features   ← ПЕРЕиспользуемые пользовательские сценарии (добавить / удалить / лайкнуть …)
  ↓
entities   ← бизнес-сущности (User, Product, Order …)
  ↓
shared     ← переиспользуемый фундамент (ui-kit, api-клиент, lib, config)
```

(`processes` между `app` и `pages` — **deprecated**: не используем, содержимое уезжает в `features` и `app`.)

Слои **необязательны** — используй только те, что приносят пользу. Типичный минимум большинства проектов: **`shared` + `pages` + `app`**. Добавлять свои слои не рекомендуется — их семантика стандартизирована.

### 🔑 Главное правило

> Модуль в слайсе может импортировать **только слайсы из слоёв СТРОГО НИЖЕ**.

- ✅ `pages` → `widgets` / `features` / `entities` / `shared`
- ✅ `widgets` → `features` / `entities` / `shared`
- ✅ `features` → `entities` / `shared`
- ✅ `entities` → только `shared` (между собой — через `@x`, см. §6)
- ❌ импорт «вверх» и cross-import слайсов одного слоя — нельзя
- ✅ внутри **своего** слайса можно импортировать что угодно (соседние сегменты и файлы)

**Исключение:** `app` и `shared` — это «слой и слайс одновременно». У них нет слайсов (только сегменты), и их сегменты **свободно импортируют друг друга**: `shared` не имеет бизнес-доменов, а `app` объединяет их все.

### Что делает каждый слой (по v2.1)

- **`app`** — всё, что касается приложения целиком: как техническое (роутер, провайдеры, глобальные стили, точка входа), так и «бизнесовое» (аналитика). Типичные сегменты: `routes`, `store`, `styles`, `entrypoint`.
- **`pages`** — страницы приложения (screens/activities). **Лимита на объём кода в слайсе страницы нет** — пока команде легко в нём ориентироваться. Здесь живут: UI страницы, loading-состояния и error boundaries (`ui`), запросы и мутации данных (`api`). Непереиспользуемый блок UI — это **часть страницы**, а не widget. Выделенный `model` у страницы — редкость: мелкие кусочки стейта можно держать прямо в компонентах. Несколько очень похожих страниц (логин + регистрация) можно объединить в один слайс.
- **`widgets`** — ⚠️ **слой не рекомендуется** (см. §0). Формально это слой для переиспользуемых блоков UI, собираемых из нескольких элементов в осмысленную секцию экрана. Проблема в том, что блок UI почти всегда несёт логику сценария (запросы, состояние, обработка событий) и начинает конкурировать с `features`. Для нового кода: композиция конкретного экрана → `pages`; переиспользуемое действие вместе с его UI → `features`; общий UI без бизнес-контекста → `shared`; layout приложения → `app`. Существующие widget-слайсы валидны, переписывать их срочно не нужно.
- **`features`** — **переиспользуемые** реализации целых продуктовых фич: действия, несущие бизнес-ценность пользователю. Ключевой принцип 2.1: **не всё должно быть фичей**. Маркер фичи — используется на нескольких страницах (например, комментарии в нескольких редакторах). Слайсы — механизм быстрого поиска кода: если фич слишком много, важные тонут в мелочи. Оптимизируй под новичка, который открывает проект впервые.
- **`entities`** — понятия реального мира, с которыми работает проект (термины бизнеса: `user`, `post`, `order`). Внутри: хранение данных и схемы валидации (`model`), запросы к API сущности (`api`), визуальное представление (`ui`). UI сущности — не обязательно законченный блок: это переиспользуемый «скелет», к которому бизнес-логику навешивают через props/slots. Взаимодействие сущностей между собой — предпочтительно **выше** (в features/pages); явные связи данных — через `@x` (§6).
- **`shared`** — фундамент: связь с внешним миром (бэкенд, библиотеки, окружение) и свои мини-библиотеки. Подробно — §14.

### Next.js (официальная рекомендация v2.1)

Папки `app/` и `pages/` заняты роутером Next.js и конфликтуют с именами слоёв FSD. Официальное решение — переименовать **оба** слоя FSD в **`_app`** и **`_pages`** (работает и с App Router, и с Pages Router; совместимо с линтером Steiger):

```
├── app/                       # Next.js App Router (тонкие ре-экспорты)
│   └── example/page.tsx       # export { ExamplePage as default, metadata } from '@/_pages/example'
└── src/
    ├── _app/                  # слой app (FSD): провайдеры, api-routes, стили
    ├── _pages/                # слой pages (FSD): вся начинка страниц
    ├── widgets/
    ├── features/
    ├── entities/
    └── shared/
```

- Роутерные папки Next.js удобнее держать в **корне проекта**, чтобы `src/` содержал только FSD-код (не обязательно).
- `middleware.ts` и `instrumentation.ts` — только в корне проекта, рядом с папками роутера.
- Route Handlers (API-роуты) — сегмент `api-routes` в слое `_app`; файлы в `app/api/**` лишь ре-экспортят оттуда. Много эндпоинтов → выноси в отдельный пакет монорепы (FSD — про фронтенд).
- Запросы к БД — сегмент `db` в `shared`; кэширование/ревалидация — рядом с самими запросами.
- Встречающееся в комьюнити имя `views/` вместо `_pages/` — рабочая альтернатива, но `_pages` понимает Steiger из коробки.

Дока: https://fsd.how/docs/guides/tech/with-nextjs

## 4. Слайсы

**Слайс** — вертикальный «срез» внутри слоя по смыслу для продукта/бизнеса (`entities/user`, `features/comments`, `pages/home`).

- Имена слайсов не стандартизированы — их диктует твой домен. Имя = домен/сценарий, а не тип (`user`, а не `models`).
- Слайсы **изолированы**: цель — *zero coupling* между слайсами одного слоя и *high cohesion* внутри слайса. Один слайс не лезет в другой — только через публичный API (`index.ts`) и только вниз по слоям.
- **`app` и `shared` слайсов не имеют** — только сегменты (см. §3).
- Слой — это **глобальный неймспейс** для своих слайсов. Как ты не засоряешь глобальную область одноразовыми переменными, так и место в неймспейсе слоя трать экономно: слайс «на один раз» обычно не нужен — см. §12.

### 4.1. Slice groups — группы слайсов (новое в доках 2.1)

Когда слайсов в слое становится много, родственные можно **сгруппировать в папку**:

```
entities/
├── payment/               # ← группа (НЕ слайс!)
│   ├── invoice/           #   ← слайс
│   │   ├── model/
│   │   └── ui/
│   ├── receipt/           #   ← слайс
│   └── transaction/       #   ← слайс
├── user/                  # ← слайс без группы — это нормально
└── product/
```

Правила групп:

- Группа — **не слайс**: у неё нет своих сегментов (`ui`/`model`/…), нет `index.ts`, и в ней **запрещён общий код** для вложенных слайсов (`payment/some-shared-code.ts` — нельзя; общее — вниз, в `shared`/`entities`).
- Группа **не меняет правила изоляции**: вложенные слайсы остаются независимыми, как будто группы нет. Это чисто навигационная структура.
- Вводи группу, когда критерий группировки **очевиден с первого взгляда** и слайсов реально много. Не вводи, если имён и так хватает для навигации, критерий натянут или в группу попадут 2–3 слайса.
- В `pages` группы отлично работают для CRUD-наборов: `pages/order/{list,detail,create}`.
- В `features` — **осторожно**: фича часто пересекает несколько сущностей, и группа вроде `features/cart/` легко превращается из навигации в «дом всего домена корзины» (туда начинают стаскивать DTO и мапперы). Сначала проверь, что слайсов достаточно и в группе — только фичи.

Дока: https://fsd.how/docs/reference/slice-groups

### 4.2. Группа или слайс — как выбрать и как чинить гибрид **[конвенция команды]**

Папка внутри слоя бывает только двух видов, третьего не дано: **слайс** (§4) или **группа** (§4.1). Отличаются они не оформлением, а тем, есть ли у папки собственный публичный **API**:

| Признак папки внутри слоя | Что это |
| --- | --- |
| есть `index.ts` и сегменты (`ui`/`model`/`lib`), вложенных слайсов нет | **слайс**; действия внутри — файлы сегментов или папки внутри них (§5.1) |
| нет ни `index.ts`, ни сегментов, а у каждой подпапки свой `index.ts` | **группа**; действия внутри — самостоятельные слайсы, снаружи адресуются поимённо |
| есть и то и другое сразу | 🚩 **гибрид — так нельзя**, см. ниже |

### 🔑 Критерий выбора: есть ли код, общий нескольким действиям

- **Общего кода нет** → каждое действие самодостаточно → это **группа** независимых слайсов. Работает тест на удаляемость (§13): сносим один слайс — ломается только его потребитель.
- **Общий код есть** (схема формы, её валидация, мапперы payload, общая форма UI) → это **одна фича**, и папка должна быть **слайсом**, а действия — жить внутри его сегментов: `model/useCreateX.ts`, `ui/form/…`, при объёме — папками `model/add-x/`, `ui/edit-x/`.

Промежуточных вариантов нет по устройству методологии: группе код держать запрещено (§4.1), а соседние слайсы не имеют права импортить друг друга (§13) — значит общему коду в разрезанном виде просто негде жить.

### Куда девать общий код — три исхода

| Что именно общее | Куда | Почему |
| --- | --- | --- |
| доменно-нейтральное (форматтеры, хелперы, UI-примитив) | вниз, в `shared` | буква §4.1 |
| данные и схемы самой сущности | вниз, в `entities/{slice}` | буква §4.1 |
| логика самого сценария: схема формы, её валидация, дефолты, UI формы | **схлопнуть группу в один слайс** | в `shared` нельзя по §14 (доменная логика), в `entities` — не по адресу: сущность не отвечает за форму фичи. Опора — §12 «не плоди слайсы» и §5.1 «папки внутри сегментов» |
| ничего из перечисленного не подходит, тянет продублировать | ⛔ дублировать нельзя | две копии схемы разъезжаются на первой же правке |

Третья строка — наше расширение поверх доки: сама §4.1 предлагает только «общее — вниз, в `shared`/`entities`».

### Чем опасен гибрид

Папка, у которой есть и свой `index.ts` с сегментами, и подпапки в форме слайсов, ломает сразу три вещи:

1. **Два входа наружу** вместо одного — общий `index.ts` и внутренние пути; §6 требует ровно один.
2. **Изоляция протекает**: подпапки начинают импортить друг друга напрямую (`edit-x/model/schema` → `../../add-x/model/schema`) — это cross-import соседних слайсов.
3. **Линтер слепнет**: сегмент вычисляется как второй уровень после слайса, поэтому у файла `promotion/create/model/hook.ts` «сегментом» считается `create`, и правила сегментов (§5: JSX в `model`, стейт в `lib`, направление `ui → model → api`) к нему просто не применяются. Проверка показывает ноль нарушений при живых проблемах.

Чинится в одну сторону: либо раздать подпапкам `index.ts` и убрать код из корня (станет группой), либо убрать подпапки-псевдослайсы, разложив их содержимое по сегментам (станет слайсом).

### Пример из наших проектов

```
features/point/                      ← ГРУППА: своего кода нет вообще
├── create/{index.ts, model/, ui/}   ← слайс с собственным API
├── delete/{index.ts, model/, ui/}
└── restore/{index.ts, model/, ui/}
    # общего кода у действий нет; снаружи: @/features/point/create

features/promotion/                  ← СЛАЙС: у действий общая схема и общая форма
├── index.ts                         ← один вход наружу
├── model/{schema.ts, useCreatePromotion.ts, useUpdatePromotion.ts, …}
├── lib/{promotions.ts, promotionStatus.ts}
└── ui/{form/…, details/…}
    # снаружи: @/features/promotion
```

Добавление нового действия поэтому выглядит по-разному: в `point` заводим новый слайс-папку со своими `model`/`ui`/`index.ts`, в `promotion` кладём хук в `model/`, модалку в `ui/` и строку в общий `index.ts`.

Форма не прибита навсегда: она следствие кода, а не вкуса. Появился у двух слайсов группы общий код — они на самом деле одна фича, группа схлопывается в слайс. Исчез общий код у слайса — он разваливается обратно на группу.

## 5. Сегменты (`ui` / `api` / `model` / `lib` / `config`)

Внутри слайса (а в `app`/`shared` — внутри слоя) код делится на **сегменты по техническому назначению** — отвечают на вопрос «**для чего этот код**».

| Сегмент      | Официальное описание (v2.1)                                                       | Наши правила поверх **[конвенция команды]**                          |
| ------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **`ui`**     | Всё про отображение: компоненты, стили, форматтеры дат и т.п.                     | Никакой бизнес-логики и запросов; чистые функции держим в `lib`.     |
| **`api`**    | Взаимодействие с бэком: функции запросов, типы данных, мапперы.                    | `try/catch` → лог → `throw` дальше (не глушить).                     |
| **`model`**  | Модель данных: схемы, интерфейсы, сторы, бизнес-логика.                            | «Мозг» слайса; без JSX.                                              |
| **`lib`**    | Библиотечный код, нужный другим модулям этого слайса.                              | Чистые функции, константы, theme-таблицы; без React-стейта и JSX.    |
| **`config`** | Конфигурация и фиче-флаги.                                                         | —                                                                    |

- Можно создавать **свои сегменты** (чаще всего это нужно в `app` и `shared`). Имя сегмента должно описывать **назначение**, а не сущность: `components`, `hooks`, `types` — **плохие имена** (не помогают искать код).
- Не обязательно заводить все сегменты сразу: у страницы часто хватает `ui` + `api`, у сущности — `model` + `api` (+ `ui`).

### 5.1. Папки внутри сегмента — можно

Сегмент — это группировка по назначению, а не плоский список файлов. Release notes 2.1 прямо поощряют дробить содержимое сегмента на папки: *«we encourage you to further split and organize code into folders inside of segments — don't just pile all the code into a single file»*. Снаружи слайса видно только его публичный API, поэтому внутренняя раскладка — дело команды.

Правило действует **на всех слоях, а не только на `entities`**: сегменты есть у каждого слайса `pages`/`widgets`/`features`/`entities`, а у `app` и `shared` сегменты живут прямо на уровне слоя (§3) — папки внутри них тоже можно. Примеры одного и того же приёма на разных слоях:

```
pages/orders/ui/components/OrdersTable.tsx      # блоки страницы
features/create-order/model/steps/…             # шаги мастера
widgets/kitchen/lib/queue/…                     # правила очереди
entities/menu/model/queries/…                   # запросы по областям
shared/lib/links/…                              # мини-библиотека сегмента shared
```

```
entities/menu/
├── model/
│   ├── queries/               # папка внутри сегмента: 44 хука не живут одним файлом
│   │   ├── menuQueries.ts
│   │   ├── dishQueries.ts
│   │   └── categoryQueries.ts
│   ├── queryKeys.ts
│   ├── queryKeys.test.ts      # тест рядом с тем, что тестирует
│   └── types.ts
├── api/
│   └── menu.ts
└── index.ts                   # единственный публичный API слайса
```

Что при этом остаётся в силе:

- **`index.ts` — только на уровне слайса.** В подпапке сегмента бареля быть не должно (§6): он замедляет дев-сервер и плодит циклы. Внутри слайса импортируем полным относительным путём — `../model/queries/dishQueries`.
- **Слои внутрь слайса не вкладываются.** `pages/checkout/features/...` — не FSD: такое предлагали, но в стандарт не приняли. Внутри слайса живут только сегменты и папки внутри них.
- **Тесты держим рядом с кодом** (`queryKeys.ts` + `queryKeys.test.ts`), а не в отдельной папке `model/test/`: смысл colocation в том, что правишь файл и сразу видишь его тест.
- **Имя папки описывает назначение**, как и имя сегмента: `queries`, `stores`, `mappers` — хорошо; `helpers`, `stuff`, `common` — плохо.

**Папки заводим по смыслу, а не по счётчику.** Не «файлов стало больше N — пора дробить», а «в сегменте видно несколько разных тем — расселяем их по папкам». Три файла про экспорт и три про фильтры в одном `lib` — это уже две папки, даже что их всего шесть. И наоборот: десять файлов про одно и то же (десять запросов одной сущности) прекрасно живут плоским списком, папка ради папки только добавит уровень вложенности. Вопрос, на который отвечает папка, — «про что этот кусок сегмента», а не «сколько тут файлов».
  
### 5.2. Что в какой сегмент — частые сомнения **[конвенция команды]**

| Что за файл | Куда | Почему |
| --- | --- | --- |
| Форматтеры дат, денег, телефонов; чистые мапперы | `lib` | функции без стейта — это библиотечный код, а не модель данных |
| `types.ts`, сторы | `model` | это и есть модель домена |
| Схемы валидации | `model` — если это модель домена; но официальная дока советует держать схему **рядом с использованием**: валидация ответа бэка → `api`, валидация формы → `ui` (§5.3) | схема ходит парой с тем, что валидирует |
| Хук с запросом, кэшем или мутацией | `model` | несёт бизнес-состояние слайса |
| Хук чисто про рендер (позиция дропдауна, фокус, размеры) | рядом с `ui` | к данным домена отношения не имеет |
| HTTP-функции и разбор ответа бэка | `api` | связь с внешним миром |

### 🔑 Принцип зависимостей сегментов **[конвенция команды]**

Официально FSD порядок импортов *между сегментами внутри слайса* не фиксирует. Мы фиксируем сами — так предсказуемее:

```
ui  →  model  →  api
ui  →  lib
model → lib
api  →  model/types   (только типы домена)
lib  →  model/types   (только типы домена)
```

- `ui` импортирует из `model`/`lib`, **не наоборот**.
- `lib` не знает про React-стейт; `model` не содержит JSX.
- Типы домена живут в `model/types.ts`, и сегменты `api` и `lib` их **читают**: функция запроса
  обязана описывать, что именно она возвращает, а чистая функция — над чем работает. Это
  единственное разрешённое обращение к `model` снизу: **только типы**, без импорта хуков, схем,
  сторов и любых значений. Вторая копия типов в `api`/`lib` запрещена — она разъедется с
  оригиналом (так уже случилось с дублем HTTP-слоя в `model/api.ts`).
- Как только в `.tsx` появляется логика/хелпер/мапа — заводи соответствующий сегмент (см. §7).

### 5.3. Типы и модели данных — где что лежит

У доки есть отдельный гайд [Types](https://fsd.how/docs/guides/examples/types) — он целиком про то, в какой слой и сегмент класть типы. Сводка:

| Что за тип | Куда | Почему так |
| --- | --- | --- |
| Утилитарные типы (`ArrayValues`, `Prettify` …) | `shared/lib/utility-types` c README — **или** рядом с местом использования | «может переиспользоваться» ≠ «будет»; в `shared` только то, что реально нужно нескольким местам |
| Типы бизнес-сущностей | `entities/{slice}/model` — либо `shared/api` рядом с запросом, если запросы живут в `shared` | тип сущности идёт за тем, кто его порождает |
| DTO (форма ответа бэка) | рядом с функцией запроса: `shared/api/*.ts` или `entities/{slice}/api/dto.ts` | DTO без запроса не имеет смысла |
| Мапперы DTO → доменная модель | там же, где DTO (`api`) | маппер принимает DTO, значит живёт рядом с его объявлением |
| Enum | максимально близко к использованию; сегмент — по смыслу значения (позиции тоста → `ui`, статусы ответа бэка → `api`, токены дизайн-системы → `shared/ui`) | «общий на весь проект» enum — редкость, а не норма |
| Схема валидации (Zod и аналоги) | ответ бэка → `api` (рядом с запросом); данные формы → `ui` рядом с формой, либо `model`, если `ui` разросся | схема — та же трансформация входных данных, что и маппер |
| Пропсы компонента, тип контекста | **в том же файле**, что компонент/контекст | для SFC (Vue, Svelte) — отдельный файл в том же `ui`-сегменте |
| Generic-типы без специфики приложения | `shared`, в сегмент по смыслу (`shared/analytics`, `shared/api` …) | — |
| `*.d.ts` для Vite / ts-reset и т.п. | `src/` или аккуратнее — `app/ambient/` | ambient-декларации не требуют архитектуры |
| Типы для нетипизированных пакетов | `shared/lib/untyped-packages/%LIB%.d.ts` | это мини-библиотека сегмента `lib`, а не свалка |
| Сгенерированные из OpenAPI/GraphQL-схемы | `shared/api/openapi` + README «как перегенерить» | генерённый код держим в одном явном месте |

> ⚠️ **`shared/types` и сегмент `types` — прямой запрет доки:** *«Resist the temptation to create a `shared/types` folder, or to add a `types` segment to your slices»*. Причина та же, что у `components`/`hooks`: имя описывает **сущность** содержимого, а не назначение, и в поиске кода не помогает. Файл `model/types.ts` внутри слайса — это другое, он разрешён (§5.2); запрещена именно папка-сегмент «типы» как категория.

**Ссылки между типами сущностей — два официальных пути.** Проблема одна: `Song` содержит `Artist`, но слайсы одного слоя друг друга не импортируют (§3).

```ts
// 1) Параметризация: слот вместо жёсткой связи
// entities/song/model/song.ts
interface Song<ArtistType extends { id: string }> {
  id: number;
  title: string;
  artists: Array<ArtistType>;
}
```

```ts
// 2) Cross-import через @x (§6) — когда развязать не выходит
// entities/song/@x/artist.ts
export type { Song } from "../model/song";

// entities/artist/model/artist.ts
import type { Song } from "entities/song/@x/artist";   // ✅ явная, видимая связь
// import type { Song } from "entities/song/model/song"; // ❌ в обход публичного API
```

Параметризация лучше работает там, где связь и правда слабая (`Cart = { items: Array<Product> }`), и плохо — там, где сущности неразделимы (`Country` / `City`).

> 🔑 **Вложенные DTO — тоже `@x`, а не хитрость.** Если бэк отдаёт песню вместе с целыми объектами артистов, сущности **обязаны** знать друг о друге. Дока прямо говорит: вместо косвенных связей (общий middleware, который раскидывает экшены по слайсам) делай явный cross-import. Связанные сущности всё равно придётся рефакторить вместе — пусть связь будет невозможно не заметить.

**Где запросы — там и свобода ссылок.** Держать запросы и DTO в `shared/api` удобно именно потому, что внутри `shared` нет слайсов и типы ссылаются друг на друга без `@x` (§3). Как только запрос переезжает в `entities/{slice}/api`, начинают действовать ограничения слоя.

**Глобальные типы, которым нужно знать всё приложение** (классика — `RootState` / `AppDispatch` в Redux без RTK): тип рождается в `app/store`, а нужен хукам в `shared/store` — это импорт «вверх», которого быть не должно. Официально рекомендованный обход — **неявная зависимость через глобальную декларацию**:

```ts
// app/store/index.ts
declare type RootState = ReturnType<typeof rootReducer>;
declare type AppDispatch = typeof store.dispatch;
```

```ts
// shared/store/index.ts
import { useDispatch, useSelector, type TypedUseSelectorHook } from "react-redux";

export const useAppDispatch = useDispatch.withTypes<AppDispatch>();
export const useAppSelector: TypedUseSelectorHook<RootState> = useSelector;
```

Дока считает это допустимым исключением: оба типа меняются редко и знакомы любому, кто писал на Redux. Разрешение точечное — на глобальные `declare` для произвольного кода оно не распространяется.

## 6. Публичный API слайса — `index.ts`

> Каждый слайс (а на слоях без слайсов — каждый сегмент) обязан иметь **публичный API**. Снаружи можно ссылаться только на него, не на внутреннюю структуру.

```ts
// ✅ через публичный API слайса
import { useUserQuery, type User } from "@/entities/user";

// ❌ лезть во внутренности слайса — нельзя
import { fetchUser } from "@/entities/user/api/fetch-user";
```

Хороший публичный API решает три задачи: (1) защищает остальной код от рефакторинга внутренностей слайса; (2) ломается компилятором при значимых изменениях поведения; (3) выставляет наружу **только необходимое**.

- **`shared`** — исключение: публичный API на уровне сегментов (`@/shared/ui/...`, `@/shared/lib/...`), а для `shared/ui` и `shared/lib` — на уровне **каждого компонента/библиотеки** (`@/shared/ui/button`), иначе страдают tree-shaking и размер бандла (тяжёлая зависимость одного компонента утянется на все страницы).

### 🔑 Только явные именованные ре-экспорты — НЕ `export *`

```ts
// ❌ нельзя — реэкспорт «всего подряд» (официально: bad practice)
export * from "./model/types";

// ✅ явный контракт — видно, что именно слайс отдаёт наружу
export type { User, UserRole } from "./model/types";
export { fetchUser, updateUser } from "./api/user";
export { useUserQuery, userQueryKeys } from "./model/queries";
```

`export *` убивает discoverability (не видно интерфейс слайса без раскопок) и случайно выставляет наружу внутренности, на которые кто-то завяжется — потом не отрефакторишь. Плюс страдают tree-shaking и авто-импорт.

### 🔑 `index.ts` живёт ТОЛЬКО на уровне слайса — не в сегментах и не в подпапках

Официальная дока прямо говорит: **избегай index-файлов в сегментах на слоях, где есть слайсы** — они замедляют дев-сервер и плодят циклы.

| Где                                               | `index.ts`?                                                    |
| ------------------------------------------------- | -------------------------------------------------------------- |
| Корень слайса (`widgets/dashboard/index.ts`)      | ✅ **да** — публичный API                                      |
| Сегмент (`.../ui/index.ts`, `.../model/index.ts`) | ❌ **нет**                                                     |
| Подпапка (`.../ui/components/index.ts`)           | ❌ **нет**                                                     |
| `shared/ui`, `shared/lib`                         | ✅ на уровне отдельного компонента/библиотеки (tree-shaking)   |

### 🔑 Внутри слайса — относительные импорты, между слайсами — абсолютные

Официальное правило против циклических импортов:

```ts
// ✅ внутри своего слайса — ОТНОСИТЕЛЬНО и полным путём (не через свой index.ts!)
import { TrendChart } from "./components/TrendChart";
import { useDashboardState } from "../model/useDashboardState";

// ✅ чужой слайс — АБСОЛЮТНО через алиас и только через его index.ts
import { useUserQuery } from "@/entities/user";

// ❌ импорт из собственного index.ts (import { x } from "../") — классический цикл
// ❌ ./components/index.ts ради «короткого списка импортов» — анти-паттерн
```

Длинный список относительных импортов в композере — **норма**. Хочешь короче — дроби на под-композеры, а не заводи барели.

### Environment-specific публичный API — `index.server.ts` (новое в 2.1)

Когда в одном слайсе живут клиентские и server-only модули (Next.js RSC), экспорт всего из одного `index.ts` ломает границу окружений: server-only side effects утекают в клиентский граф модулей и валят сборку. Решение — **когда проблема реально возникла** — добавить рядом `index.server.ts` и экспортировать оттуда Server Components и функции с `server-only`.

### Cross-import между сущностями — `@x` (стандартизировано в 2.1)

Слайсы одного слоя не импортируют друг друга, но сущности в реальном мире ссылаются друг на друга — и это лучше отразить явно, чем обходить. Если `entities/B` нужен тип из `entities/A`, сущность A объявляет **отдельный публичный API специально для B**:

```
entities/A/
├── @x/
│   └── B.ts          # export type { EntityA } from "../model/a";  ← API только для entities/B
└── index.ts          # обычный публичный API
```

```ts
// entities/B/model/b.ts
import type { EntityA } from "entities/A/@x/B";   // читается: «A crossed with B»
```

Применять **только на слое `entities`** и по минимуму: связанные сущности рефакторятся вместе, поэтому связь должна быть невозможной не заметить.

### Монорепа для очень больших проектов

Если проект гигантский (условный «редактор + файловый менеджер» как в Google Docs) — режь его на пакеты монорепы, каждый пакет = **отдельный FSD-корень** со своим набором слоёв. Одни пакеты могут иметь только `shared` + `entities`, другие — только `pages` + `app`.

Дока: [Public API](https://fsd.how/docs/reference/public-api).

## 7. Тонкий компонент — без God Object **[конвенция команды]**

FSD 2.1 разрешает «толстые» **слайсы** (особенно страницы), но не «толстые» **файлы**: официальная позиция — код внутри слайса всё равно режется по сегментам и папкам, «не сваливай всё в один файл». Наше правило делает это конкретным:

> **Файл компонента (`.tsx`/`.vue`) = сегмент `ui` = чистая презентация.** Только разметка, условный рендер и проброс пропов. Всё остальное — в `model/` и `lib/` того же слайса.

### Что НЕЛЬЗЯ оставлять inline в компоненте

1. **Логику состояния** — пачку `useState`/`useEffect`, синхронизацию с URL, оркестрацию запросов/мутаций, обработчики >5 строк → **один кастомный хук** `model/use{Name}.ts`, возвращающий объект:
   ```ts
   const { state, options, handlers, query } = useDashboard();
   ```
2. **Чистые функции** (`buildX()`, форматтеры, мапперы, билдеры URL) → `lib/{topic}.ts`.
3. **Константы и lookup-мапы** (`const STATUS = [...]`, `const TONE: Record<...>`) → `lib/{topic}.ts` (или `*-theme.ts` со стилевыми геттерами).
4. **Под-компоненты** (любая `function Row()/Card()` под главным экспортом) → `ui/components/{SubName}.tsx`.
5. **Тяжёлые `useMemo`/трансформы данных** → в `model`/`lib`; в компонент приходит готовое.

### Триггеры «пора дробить»

- файл компонента **> 200–300 строк** (мягкий триггер), **> 400 строк — запрещено**;
- в файле **больше хуков/хендлеров, чем разметки**;
- приходится **скроллить**, чтобы понять компонент;
- появился `function foo()` или `const MAP = {...}` на уровне модуля в `.tsx` → **стоп, выноси.**

### Правило большого пальца

- **Компонент-композер** = последовательность секций с пропами из хука. Без локального стейта, без `buildX()`, без инлайн-мап.
- **Один большой хук на тяжёлый компонент** — дефолтная цель рефакторинга. Возвращай всё, что нужно разметке, одним объектом.

## 8. Где что лежит (шпаргалка)

| Что                                       | Куда                                       |
| ----------------------------------------- | ------------------------------------------ |
| UI и логика, нужные ОДНОЙ странице        | `pages/{slice}/ui` / `model` / `lib` — не выноси! |
| Запросы/мутации одной страницы            | `pages/{slice}/api`                        |
| Loading-состояния / error boundary страницы| `pages/{slice}/ui`                        |
| Чистый хелпер для 1 слайса                | `{layer}/{slice}/lib/*.ts`                 |
| Стилевые/theme-мапы                       | `{layer}/{slice}/lib/*-theme.ts` (геттеры) |
| Под-компонент только этого слайса         | `{layer}/{slice}/ui/components/*.tsx`      |
| Локальный стейт-хук / оркестрация         | `{layer}/{slice}/model/use*.ts`            |
| Кэш-запросы/мутации сущности              | `entities/{slice}/model/queries.ts`        |
| HTTP-функции сущности                     | `entities/{slice}/api/*.ts`                |
| Типы домена                               | `entities/{slice}/model/types.ts`          |
| Действие, переиспользуемое на 2+ страницах| `features/{slice}`                         |
| Блок, переиспользуемый на 2+ страницах    | ⚠️ не `widgets` (слой не рекомендуется, §0): действие вместе с его UI → `features/{slice}`, UI без бизнес-контекста → `shared/ui`, layout приложения → `app` |
| DTO и маппер ответа бэка                  | рядом с запросом: `{layer}/{slice}/api/` или `shared/api/` (§5.3) |
| Схема валидации (Zod)                     | ответ бэка → `api`; форма → `ui` рядом с формой (§5.3) |
| Enum                                      | ближе к использованию, сегмент по смыслу значения (§5.3) |
| Типы для нетипизированного пакета         | `shared/lib/untyped-packages/%LIB%.d.ts`   |
| Хелпер, нужный в 2+ слайсах               | `shared/lib/{область}/*.ts`                |
| UI-примитив, нужный везде                 | `shared/ui/{component}` (свой index.ts)    |
| Публичный API слайса                      | `{layer}/{slice}/index.ts`                 |

## 9. Конвенции **[конвенция команды]**

### Именование

- **Слайсы/папки:** по домену/сценарию (`user`, `comments`, `home`), не по типу.
- **Компоненты:** `PascalCase` (`UserCard.tsx`).
- **Хуки:** `useXxx`.
- **Запросы/мутации:** `useXxxQuery` / `useXxxListQuery` / `useXxxMutation`.
- **HTTP-функции:** `fetchXxx` / `createXxx` / `updateXxx` / `deleteXxx`.
- **Ключи кэша:** объект-фабрика `xxxQueryKeys` со значениями `as const`.

### Импорты

- Алиас на корень: `@/*`.
- Чужой слайс — **только из его `index.ts`**, абсолютным путём.
- Внутри своего слайса — относительные пути (§6).
- Типы — отдельной строкой: `import type { User } from "@/entities/user"`.

### Серверное vs клиентское состояние

| Данные                              | Где живут                             |
| ----------------------------------- | ------------------------------------- |
| Всё, что приходит с бэка            | кэш-слой (напр. TanStack Query)       |
| Локальный UI-стейт (таб, модалка)   | `useState` в компоненте/странице      |
| Глобальный UI-стейт (тема, сайдбар) | стор (напр. Zustand) в `shared/model` |
| Токен/сессия                        | хранилище + зеркало в сторе           |

> Не дублируй серверные данные в клиентский стор — источник истины один (кэш-слой).

### Обработка ошибок по слоям

- **`api`:** `try/catch` → залогировать → `throw` дальше (не глуши).
- **хук фичи/страницы:** поймать → показать тост → пробросить, если нужно.
- **`ui` форма:** поймать сабмит → подсветить ошибку (`root`-ошибка формы).

## 10. Эталонные структуры слайсов

### Страница (типичный случай в 2.1 — большая часть кода живёт здесь)

```
pages/dashboard/
├── api/
│   └── get-dashboard.ts         # запросы этой страницы (не переиспользуются — значит здесь)
├── model/
│   └── useDashboardState.ts     # стейт + URL-sync + сбор параметров + handlers (хук)
├── lib/
│   ├── filters.ts               # константы, readFilters(), buildUrl(), мапперы — чистый код
│   └── insights.ts              # чистые билдеры данных
├── ui/
│   ├── DashboardPage.tsx        # КОМПОЗЕР: только JSX, дёргает useDashboardState() + рендерит блоки
│   └── components/              # блоки ТОЛЬКО этой страницы — им не нужен слой widgets
│       ├── FilterBar.tsx
│       ├── TrendChart.tsx
│       └── SlaTiles.tsx
└── index.ts                     # export { DashboardPage } from "./ui/DashboardPage";
```

Композер в идеале выглядит так:

```tsx
export function DashboardPage() {
  const { state, options, handlers, query } = useDashboardState();
  if (query.isPending) return <Skeleton />;
  if (query.isError) return <ErrorState />;
  const data = query.data;
  return (
    <Layout>
      <FilterBar {...options} onChange={handlers.setFilter} />
      <TrendChart data={data.trends} />
      <SlaTiles sla={data.sla} />
    </Layout>
  );
}
```

### Widget — ⚠️ слой не рекомендуется

Структура та же (`model` + `lib` + `ui` + `index.ts`) в `widgets/{name}/`, и в существующих проектах она остаётся рабочей. Но для **нового** кода дока рекомендует не заводить widget: разложите блок по таблице из §0 — экранная композиция в `pages`, переиспользуемое действие с его UI в `features`, нейтральный UI в `shared`, layout в `app`.

## 11. Чек-лист нового кода

1. **Сначала спроси: это нужно больше чем в одном месте?**
   - Нет → живёт **в слайсе страницы** (в её `ui`/`api`/`model`/`lib`). Всё, стоп, слайс не нужен.
   - Да / станет нужно → шаг 2.
2. Определи **слой** по смыслу (§12): переиспользуемое действие (вместе с его UI) → `features`; понятие домена → `entities`; доменно-нейтральное → `shared`; layout приложения → `app`. Новый слайс в `widgets` не заводим (§0).
3. Заведи папку слайса и нужные **сегменты** (`ui`, `api`, `model`, `lib`, …).
4. Сущность: `model/types.ts` → `api/*.ts` → `model/queries.ts` → (опц.) `ui/`.
5. Фича: `model/schema` (валидация + дефолты) → `model/use{Action}.ts` (обёртка над мутацией) → `ui/*.tsx`.
6. Экспортируй наружу только через `index.ts` (именованно, без `export *`).
7. Проверь правило импортов (только вниз; внутри — относительные, снаружи — абсолютные) и тонкость `.tsx` (§7).
8. Прогони `npx steiger src` — он подскажет, если нарезал лишнего.

## 12. Какой слой выбрать — эвристика v2.1

**Дефолт — страница.** Не уверен → клади в `pages/{текущая-страница}`: переезд вниз при появлении второго потребителя дешевле, чем распутывание преждевременных абстракций.

| Слой           | Вопрос-маркер                                              | Признак                                              | Примеры                               |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------- |
| **`pages`**    | «это используется на одной странице?»                      | да → живёт здесь, включая формы, блоки и запросы     | `home`, `dashboard`, `order-list`     |
| **`widgets`** ⚠️ | слой **не рекомендуется** — см. §0 | вместо него: `pages` / `features` / `shared` / `app` | — |
| **`features`** | «действие переиспользуется на 2+ страницах?» (глагол)      | пользовательский сценарий с бизнес-ценностью         | `comments`, `login`, `add-to-cart`    |
| **`entities`** | «что ЕСТЬ в системе?» (существительное)                    | данные понятия домена + их переиспользуемое отображение | `user`, `post`, `order`            |
| **`shared`**   | «это вообще про бизнес-логику?»                            | нет — инфраструктура/фундамент                       | `Button`, `api-клиент`, `formatDate`  |

- Сомневаешься **feature vs entity** → «это про *данные* (сущность) или про *действие*?».
- Сомневаешься **feature vs page** → «это переиспользуется где-то ещё?» Нет → это просто часть страницы.
- Сомневаешься **widget vs что-то ещё** → widget не заводим вовсе: экранная композиция → `pages`, переиспользуемое действие с UI → `features`, нейтральный UI → `shared`, layout → `app` (§0).
- ⛔ Анти-правило 2.1: **не плоди слайсы.** Место в неймспейсе слоя ценно; фича/сущность «на один раз» топит важное в мелочи.

## 13. Изоляция слайсов и тест на удаляемость

- Цель — **zero coupling между слайсами одного слоя, high cohesion внутри слайса**: `entities/task` **не** импортит `entities/project` напрямую. Нужна связь — три варианта:
  1. подними взаимодействие **выше** (в feature/страницу, которая видит обе сущности) — предпочтительный путь по 2.1;
  2. `@x`-нотация (только `entities`, по минимуму, для явных связей данных);
  3. опусти общее **ниже**, в `shared`.
- Группа слайсов (§4.1) изоляцию **не отменяет** и общего кода не содержит.
- 🧪 **Тест на high cohesion:** *слайс можно удалить, и сломаются только его явные потребители.* Если удаление одного слайса тянет правки по всему слою — связность плохая, код размазан.
- На практике: всё про одну страницу/сущность/сценарий лежит **в одном слайсе** (cohesion), а наружу слайс торчит **минимальным `index.ts`** (coupling).

## 14. `shared` — фундамент приложения

`shared` — связь с внешним миром (бэкенд, библиотеки, окружение) и собственные мини-библиотеки. Здесь **нет бизнес-логики**, но — уточнение 2.1 — «business-themed» вещи допустимы.

Типичные сегменты:

- **`api`** — настроенный API-клиент (+ при желании функции запросов к конкретным эндпоинтам).
- **`ui`** — UI-kit приложения. Без бизнес-логики, но **бизнес-тематика — ок**: логотип компании, layout страницы. Компоненты с UI-логикой (autocomplete, search bar) — тоже ок.
- **`lib`** — набор **сфокусированных мини-библиотек**, а не свалка «utils/helpers». Каждая — про одну область (даты, цвета, работа с текстом), с README, чтобы команда знала, что туда можно и нельзя добавлять.
- **`config`** — env-переменные, глобальные фиче-флаги.
- **`routes`** — константы/паттерны роутов.
- **`i18n`** — сетап переводов, глобальные строки.
- **`db`** — запросы к БД (для fullstack-фреймворков типа Next.js).

Правила:

- 🚩 **Признак нарушения:** доменная *логика* или *данные* в `shared` (`shared/lib/calculate-order-total.ts`) → это `entity`/`feature`/страница. Чисто визуальные бизнес-темы (лого, layout) — можно.
- `shared` **не имеет слайсов** — только сегменты; сегменты свободно импортируют друг друга.
- Публичный API — на уровне сегмента, а для `shared/ui` и `shared/lib` — **на каждый компонент/библиотеку** (`@/shared/ui/button`), см. §6.

## 15. Инструменты — как ГАРАНТИРОВАТЬ соблюдение

Дисциплина не масштабируется: правило «импортируй только вниз» держится, пока о нём помнят. Поставь автоматику:

- **Steiger** — официальный линтер: `npm i -D steiger @feature-sliced/steiger-plugin`, запуск `npx steiger ./src` (`--watch` для локальной работы). Гоняй в **CI** — нарушения границ падают на PR, а не всплывают через полгода.

  > ⚠️ **Два пакета, не один.** Сам `steiger` — универсальный линтер файловой структуры, правил FSD в нём нет. Их приносит плагин `@feature-sliced/steiger-plugin`, и в конфиге правила адресуются с префиксом — `'fsd/public-api'`. Версии на 09.09.2026: `steiger@0.6.0`, `@feature-sliced/steiger-plugin@0.7.0` (обе от 14.07.2026, проверено по npm).

  Конфиг не обязателен (zero-config); нужен, только чтобы что-то отключить — `steiger.config.ts` через `cosmiconfig`, формат в духе flat-config ESLint:

  ```ts
  // steiger.config.ts
  import { defineConfig } from "steiger";
  import fsd from "@feature-sliced/steiger-plugin";

  export default defineConfig([
    ...fsd.configs.recommended,
    { files: ["./src/shared/**"], rules: { "fsd/public-api": "off" } },
    { ignores: ["**/__mocks__/**"] },
  ]);
  ```

  > 💡 Формат конфига сменился в `0.5.0` — для старых проектов в репозитории есть codemod (`MIGRATION_GUIDE.md`). Сам проект помечен как **beta**: API правил ещё может меняться.

  > 💡 С версии плагина `0.6.0` разбор импортов переехал на **tree-sitter**, и появилась поддержка `.astro` и `.svelte` — раньше эти файлы просто не анализировались. В ядре `0.6.0` добавили профилирование и слежение за файлами в `--watch`.

  Набор правил плагина `0.7.0` — **20 штук**, из них 17 включены пресетом `recommended` и 3 выключены по умолчанию (сверено с распакованным npm-пакетом 09.09.2026).

  **Включены в `fsd.configs.recommended`:**

  | Правило | Что ловит |
  | --- | --- |
  | `forbidden-imports` | импорт «вверх» по слоям и cross-import слайсов |
  | `public-api` | у слайса (или сегмента на слоях без слайсов) нет публичного API |
  | `no-public-api-sidestep` | импорт напрямую во внутренности слайса в обход `index.ts` |
  | `no-layer-public-api` | `index.ts` на уровне **слоя** (так нельзя) |
  | `no-segments-on-sliced-layers` | сегменты прямо в слое, у которого есть слайсы |
  | `no-segmentless-slices` | слайс без сегментов |
  | `segments-by-purpose` | сегменты вида `components` / `hooks` / `types` (в `0.7.0` список расширен) |
  | `insignificant-slice` | слайс используется только на одной странице → влить в страницу |
  | `excessive-slicing` | в слое слишком много слайсов → слить или сгруппировать (§4.1) |
  | `ambiguous-slice-names` | имя слайса совпадает с именем сегмента в `shared` |
  | `repetitive-naming` / `inconsistent-naming` | несогласованные имена слайсов (единственное/множественное число) |
  | `typo-in-layer-name` | опечатка в имени слоя |
  | `no-reserved-folder-names` | подпапка сегмента названа как другой канонический сегмент |
  | `no-processes` | использование deprecated-слоя `processes` |
  | `no-ui-in-app` | сегмент `ui` в слое `app` |
  | `shared-lib-grouping` | `shared/lib` как свалка вместо сфокусированных библиотек |

  **Выключены по умолчанию — включать вручную:**

  | Правило | Что ловит |
  | --- | --- |
  | `no-higher-level-imports` | только импорты «вверх» по слоям |
  | `no-cross-imports` | только cross-import между слайсами одного слоя |
  | `import-locality` | относительные/абсолютные импорты не по правилу (§6) |

  > ⚠️ **`forbidden-imports` и пара `no-higher-level-imports` + `no-cross-imports` — это одно и то же, разрезанное надвое.** Гранулярные правила появились в `0.5.6` как замена, но старое оставлено для обратной совместимости и включено в `recommended`. Если включаешь новые — **выключай `forbidden-imports`**, иначе получишь дубли диагностик. Официальная формулировка: *«The `forbidden-imports` rule still remains for backward compatibility. If you want to use the new rules, enable them explicitly in the config and disable the `forbidden-imports` rule.»*

  > ⚠️ **Правила `no-file-segments` в поставке нет.** В репозитории лежит каталог `packages/steiger-plugin-fsd/src/no-file-segments/` с реализацией, README и тестами, но он не импортируется в `src/index.ts` и не попадает в собранный пакет (проверено grep'ом по `dist` версии `0.7.0` — ноль вхождений). Последний коммит туда — март 2025. Проверку «сегмент-файл вместо сегмента-папки» Steiger **не делает**; в наших `fsd-scripts` она есть.
- **ESLint** — `@feature-sliced/eslint-config` (⚠️ `0.1.1`, последняя публикация 30.04.2024, последний коммит — октябрь 2024, в README висит «WIP: at the moment at beta-testing»; формально не deprecated, но фактически заморожен и написан под legacy `.eslintrc`, flat-config ESLint 9 не поддерживает — это решение эпохи FSD 2.0, официальным линтером команда называет Steiger) или живой `eslint-plugin-boundaries` (`7.2.0`, август 2026): запрет импортов «вверх» и в обход `index.ts` прямо в IDE. Важно: `index.ts` сам по себе ни от чего не защищает — авто-импорт IDE легко ходит в обход, ловить это может только линтер.
- **Алиас `@/*`** (tsconfig `paths`) — пути от корня, а не `../../../`.

> Минимум для команды: `steiger` в CI. Остальное — приятный бонус для DX.

> 💡 **Редакторная интеграция на подходе.** В `master` Steiger лежит **language server** (бинарь `steiger-language-server`, добавлен 29.07.2026 — уже после релиза `0.6.0` от 14.07.2026), а рядом развивается VS Code-расширение `feature-sliced/steiger-vscode`. Это даст подсветку нарушений FSD прямо в редакторе, но на npm по состоянию на 09.09.2026 языкового сервера ещё нет — только в исходниках.

## 16. Анти-паттерны / частые ошибки (чек-лист ревью)

Увидел — разворачивай:

- 🪤 **Фича-однодневка:** entity/feature используется на одной странице → влить в страницу (правило `insignificant-slice`).
- 🔪 **Пере-нарезка:** десятки микро-слайсов в слое, важное тонет в мелочи → слить или сгруппировать (`excessive-slicing`, §4.1).
- 🧱 **Толстый `.tsx`:** логика / `useEffect` / мапы в render-дереве → в `model`/`lib` того же слайса (§7).
- 🏷️ **Доменная логика в `shared`** (`shared/lib/order-total.ts`) → это страница/`feature`/`entity` (§14).
- 🗂️ **Папка `shared/types` или сегмент `types` в слайсе** → раскладывать по назначению: DTO рядом с запросом в `api`, доменные типы в `model`, утилитарные — в `shared/lib/utility-types` (§5.3).
- 🧷 **Импорт типа сущности напрямую из соседнего слайса** (`entities/song/model/song`) → параметризовать тип или объявить `@x`-API (§5.3, §6).
- 🗑️ **`shared/lib` как свалка utils/helpers** → сфокусированные библиотеки с README (§14).
- 🪜 **Импорт «вверх»** (`entity` тянет `feature`) → перевернуть зависимость или поднять взаимодействие выше (§3).
- 🔓 **Импорт в обход `index.ts`** (`@/entities/user/api/fetch-user`) → только через публичный API (§6).
- 🧩 **Cross-import между слайсами одного слоя** напрямую → поднять выше или `@x` на entities (§6, §13).
- 🛢️ **Барель `index.ts` в сегменте/подпапке** → удалить, внутри слайса импортить напрямую (§6).
- 📦 **Общий код в папке-группе слайсов** → группам нельзя иметь код, только слайсы (§4.1).
- 🧬 **Папка одновременно слайс и группа** (свой `index.ts` и сегменты + подпапки в форме слайсов) → выбрать одно из двух по §4.2.
- 🎭 **Новый слайс в `widgets`:** слой официально не рекомендуется → разложить по §0 (`pages` / `features` / `shared` / `app`).
- 🔁 **Дублирование серверных данных в сторе** → источник истины один: кэш-слой (§9).
- 🖥️ **Server-only код в общем `index.ts`** (Next.js RSC) → вынести в `index.server.ts` (§6).
